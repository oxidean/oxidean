- Error vocabulary still conforms to C1: `auth.forbidden`, `invalid_provider`, `bad_input` (generic proc-layer code), `crypto.unavailable` (500-class for a missing secrets-key source — the encryption chain, not the provider api_key; now unambiguous in BR1.2's context). New `settings_set` request fields (`api_key`, `clear_key`, `clear_overrides`) and the get shape's `*_overridden` flags are contract-additive per the ownership rules; `enabled_override` remains the tri-state write field while the get emits effective `enabled` + `enabled_overridden`, matching the mcp precedent.
- Minor residual ambiguities noted but not raised as findings: whether `clear_overrides` + `api_key` in one payload ignores the key (precedence) or still trips the pair-conflict `bad_input`; whether an empty advertised `models` list (e.g. for ollama, whose model set is operator-pulled) means "no model constraint"; whether `key_last4` is emitted for env-sourced keys or only stored keys; and prod `OXIDEAN_OXPILOT_PROVIDER=stub` remaining env-selectable while `settings_set` refuses it outside test builds (asymmetric but deliberate, matches shipped U1).
- entities.md relationship `OxpilotRuntimeSlot --materializes--> EffectiveProviderConfig` reads backwards relative to its own description ("slot state IS the resolved projection" — the config materializes INTO the slot); cosmetic.
