### Notes

- Verified correct (no action): `crypto.rs` `encrypt(env_keys, plaintext) -> Result<String,String>` returns `hex(nonce||ciphertext)` exactly as the design assumes; `decrypt` returns plaintext `String`; the KEY_ENVS fallback chain mirrors `actions/secrets.rs:8,47-53` verbatim. No `last4` helper exists — `key_last4` is correctly a new hand-rolled helper (edge worth one line: on a key shorter than 4 chars it emits the entire secret; bound it with `min(4, len)` or a minimum-key-length check).
- Auth surface verified: `require_admin` (auth/admin.rs:20-38) emits exactly `auth.unauthenticated`/`admin.forbidden`/`auth.banned`; `auth.pat_scope` is raised pre-dispatch by the SessionOnly catch-all (`classify_pat_proc` fail-closed, pat/bearer.rs). `admin.oxpilot.*` joining api-oxpilot's own PROCEDURES+dispatch is consistent with the shipped closed-set pinning test (lib.rs:31-75) — note it diverges from the `admin.mcp.*` precedent of living in `oxidean-api-admin`, but BR5.4 explicitly pins the in-crate placement.
- Lock discipline verified safe: the only acquisition order is `rebuild_lock` -> `slot.write()` for a single assignment; request-path readers take `slot.read()` alone; no path takes the slot lock then the mutex, so no deadlock cycle exists. `tokio::sync` primitives are the right choice — no std guard is held across an `.await` in any drawn path (the sync `RwLock` precedent `email_slot`, settings.rs:157, is a different, instant-only pattern).
- The enablement design claim is coherent: the slot IS the DB-aware projection — `oxpilot_settings` is read at rebuild (boot + settings_set), never per request; `resolve_enablement`'s "DB-aware" nature lives in the rebuild resolver, not the read path. No contradiction found.
- No custody hole found in the design: plaintext enters via `encrypt_key` (persisted as ciphertext+last4 only) and via decrypt inside `providers::build` (adapter memory); `settings_get` reads stored `key_last4` or env-key last4 — no decrypted material crosses a read path AS DRAWN (the producer ambiguity on `api_key_plaintext` is filed under R-05/R-12).
- Multi-replica bound (NFR3.15), redirect `Policy::none()` + manual 3xx classification, connect-phase-only retry (`is_connect()` — the doc's stray `is_connect_error()` spelling should be normalized), connect 10s/total 300s timeouts, and the `mcp_settings` singleton tri-store precedent (seeded row, per-dialect UPDATE) all check out against shipped code.
- C4 trait delta is upstream-sanctioned (FD Q7) and C1's admin-proc shapes match the design, but adding `ToolCall`/`Done{usage}` variants breaks run_turn's exhaustive match — expected under BR5.5's same-PR rule; the payload homes are filed under R-12.
- `dialect_oxpilot.rs` already exists in oxidean-db tests (U1 artifact), so BR5.4's "extends" wording is accurate; the `oxpilot_settings` migration should copy mcp_settings' seeded-singleton INSERT pattern (all three dialects seed id=1).
