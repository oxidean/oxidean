### Review — connector-gateway functional-design, iteration 1

**Reviewer:** aidlc-architecture-reviewer-agent
**Iteration:** 1
**Verdict:** NOT-READY

### Review
Checked `entities.md`, `rules.md`, `functional-spec.md`, and `traceability.json` for U6 against the C1/C3/C5/C7/C8 contract pins, FR5.1–5.6/FR6.6/NFRs, AC4.x/AC5.x, components.md §ConnectorGateway, and shipped code (`oxidean-api-core/src/oxpilot.rs` SessionService/SessionDeleteHook/runtime slot, `pat/bearer.rs` sha256+FailedAuthLimiter precedent, `api-oxpilot/routes.rs` session-auth edge, `api/main.rs` hook registration order, `services.rs` hook-then-cascade, and the 0085/0087 migrations' `ON DELETE CASCADE` convention). The artifacts are unusually thorough — secret custody, lazy expiry, ordered dispatch checks, atomic redeem, and audit discipline are all well-formed, and the traceability covers every owned upstream id with defensible Deferreds. However, iteration 1 carries three contract-breaking/consent-bypass defects, and a dozen design gaps that will produce real defects: two mutually-contradictory rule pairs, an unimplementable C7 signature (no user context), an unreachable `running` state (no C3 message can trigger it), a missing re-pair and re-consent mechanism, an unspecified FK story that can either break session delete or destroy the audit trail it exists to preserve, and several state-machine dead ends (stranded `queued` rows, unclosable `cancel_requested` rows, stranded `pending_consent` targets). Every critical/major item has a concrete fix path.

### Disposition notes
- Deliberate but worth re-confirming: `Action.args` stores the *redacted* dispatch args and claim delivers them verbatim — so a command containing a secret-shaped literal executes in altered form. That is the mandated custody posture, but consider an explicit sentence that execution-vs-intent divergence is intended fail-closed behavior.
- Also unflagged but recommended for the next iteration: dequeue/revoke/respond mutations must all be *state-conditional* updates (UPDATE … WHERE state=…) inside the per-target lock for the atomicity claims in BR4.1/BR5.1/BR6.x to hold; `grant_respond`/`target_revoke` serialization under the same per-target lock as dispatch is implied but never stated; and rate-limit on `/pair` itself is defensible to omit given ≥160-bit code entropy but deserves one line saying so.
