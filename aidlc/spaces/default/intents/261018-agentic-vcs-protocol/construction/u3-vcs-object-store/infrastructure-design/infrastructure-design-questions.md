# Infrastructure Design — Questions (u3-vcs-object-store)

Library unit — no deployment surface of its own. Its runtime resources are the host's (objects dir on the server filesystem, DB via the existing facade). The produce set is cicd-pipeline.md + traceability.json: the question that matters is how the `server` cargo feature actually reaches CI, because every existing lane runs default features and would compile zero U3 code.

**Q1 — How do U3's `server`-feature tests reach CI without breaking the no-compile-on-shards invariant?**

[Answer]: One flag on the existing archive. `rust-build` (ci.yml:198-208) runs `cargo nextest archive --workspace` — default features, so `#[cfg(feature = "server")]` code and `#[cfg(all(test, feature = "server"))]` tests never compile. Under `resolver = "2"` (root Cargo.toml:2, RFC-2957), `cargo nextest archive --workspace --features server` enables `server` on every selected package *that declares it* — only `oxidean-vcs` — so the single `nextest-archive` then contains the server-gated test binary and the `api-rust` shards execute it for free (partitioned across the matrix — each test lands on exactly one shard). Considered and rejected: (a) a second `cargo nextest archive -p oxidean-vcs --features server` artifact + dedicated job — works, but adds an artifact, an upload, `rust-artifacts-cleanup` wiring (needs + jq select at ci.yml:891-915), and a job for the same coverage; (b) `cargo nextest run -p oxidean-vcs --features server` inside a shard — violates the no-compile invariant (server tests dev-depend on `oxidean-db`+`tempfile` → fresh sqlx/tokio compile on a runner with no cooked `/ci/target-dev`). Residual under the chosen design: if `--features server` is accidentally dropped, the suite regresses to silence — mitigated by the dedicated `-E 'package(oxidean-vcs)'` leg in cicd-pipeline.md (empty filter → NO_TESTS_RUN loud failure).

**Q2 — Which existing gates also need feature-aware additions?**

[Answer]: Three. `dead-code` job (ci.yml:329-334): add `cargo clippy -p oxidean-vcs --all-targets --all-features -- -D warnings` alongside the workspace clippy, and `RUSTDOCFLAGS="-D warnings" cargo doc -p oxidean-vcs --no-deps --features server` alongside the workspace doc — both carry the job's existing `-D warnings` parity. `cargo machete` (ci.yml:331): feature-gated optional deps (`dep:` under `server`) can false-positive as unused — pin `[package.metadata.cargo-machete] ignored` entries in `crates/oxidean-vcs/Cargo.toml` if needed (api's precedent at Cargo.toml:106-107). Makefile lanes (LC3.6): `test` nextest arm + `cargo test` fallback arm + `dead-code-check` + `docs-check` — the Makefile is what developers and the checkpoint's recorded command actually run.

**Q3 — Any infra/resource provisioning to design?**

[Answer]: None. `OXIDEAN_VCS_OBJECTS_DIR` is host filesystem config (env contract BR3.7 — validated by `ObjectStoreConfig::from_env`, marker-gated by SD3.8). No new DB resources (facade reuse, zero migrations — NFR6). GC scheduling is a host job (U7 wiring, `gc_interval_secs=0` disables). The objects dir is a sibling of the existing LFS `OXIDEAN_LFS_DIR` convention — operators provision it the same way; the `from_env` sibling-dir equality refusal (SD3.9-R7) prevents pointing it at the LFS dir.
