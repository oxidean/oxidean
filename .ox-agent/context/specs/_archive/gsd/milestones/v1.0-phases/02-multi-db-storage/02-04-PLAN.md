<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host `./var` → api container `/app/var` | Bind-mounted SQLite database file crosses the container boundary |
| Operator shell env (`DATABASE_URL`) → Make/scripts | Connection strings with credentials pass through command lines and logs |
| `make db-switch-dialect` → target database | A destructive-looking operation pointed at a possibly populated database |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Information disclosure | SQLite file committed to git | mitigate | `.gitignore` gains `var/`; `make up-sqlite` creates `./var` up front so Docker does not create a root-owned directory |
| T-02-12 | Information disclosure | credentials echoed by smoke/switch scripts | mitigate | Scripts print the dialect and target host only; `DATABASE_URL` is never echoed and `set -x` is not used |
| T-02-13 | Tampering | dialect switch against a populated database | mitigate | `scripts/db-switch-dialect.sh` delegates to `migrate --assert-empty`, exits non-zero on a non-empty target, and never issues DROP/TRUNCATE — `--force-empty` is an explicit operator opt-in that still only runs migrations |
| T-02-14 | Spoofing | smoke passing against the wrong database | mitigate | Smoke asserts `"dialect":"<expected>"` from the `system.db_probe` response body, not merely HTTP 200 |
| T-02-15 | Denial of service | stale volumes/containers between dialect runs | accept | Local-only; smoke `trap`s a `compose down --remove-orphans` for the exact overlay set it started |
</threat_model>

  <files>docker-compose.sqlite.yml, .gitignore</files>

  <action>
Locks RESEARCH open item 1. Compose merges mappings and cannot delete keys, so removing the Postgres dependency requires the Compose `!reset` tag (Compose v2.24+) rather than a naive redeclaration.

1. Create `docker-compose.sqlite.yml`:

```yaml
# SQLite overlay (D-07, D-19): no DB container, file bind-mounted from ./var.
#   docker compose -f docker-compose.yml -f docker-compose.sqlite.yml up --build
# Requires Docker Compose v2.24+ for the !reset tag.
services:
  postgres:
    profiles: ["postgres"]

  api:
    depends_on: !reset null
    environment:
      DATABASE_URL: sqlite:/app/var/oxidean.db
      OXIDEAN_DB_DIALECT: sqlite
    volumes:
      - ./var:/app/var
```

   Two mechanisms are needed together: `profiles: ["postgres"]` keeps the Postgres service out of the default `up` set for this overlay, and `depends_on: !reset null` drops the api→postgres dependency so Compose does not auto-enable the profiled service. The base `docker-compose.yml` is left untouched, so plain `docker compose up` and `make up` keep the Phase 1 Postgres default (D-06).
2. Verify the resolved config before trusting it (RESEARCH pitfall 8): `docker compose -f docker-compose.yml -f docker-compose.sqlite.yml config` must succeed, must **not** list a `postgres` service, and the `api` service must have no `depends_on` on postgres and must carry the `./var:/app/var` bind mount. If the installed Compose rejects `!reset`, record the version in the SUMMARY and fall back to `depends_on: !override {}`; do not fall back to `--scale postgres=0`.
3. Add `var/` to `.gitignore` (next to the existing `data/` entry) — the SQLite database and WAL/SHM sidecars must never be committed (T-02-11).
4. `docker-compose.mysql.yml`: add `OXIDEAN_DB_DIALECT: mysql` to the `api` environment so the mysql path exercises the D-01/D-02 agreement check too. No other change.
  </action>
  <verify>docker compose -f docker-compose.yml -f docker-compose.sqlite.yml config &amp;&amp; docker compose -f docker-compose.yml -f docker-compose.sqlite.yml config | grep -q '/app/var'</verify>

  <action>
Extend the existing script rather than forking a second one (its Docker-Desktop/WSL discovery block stays untouched).

1. Parameterise the compose invocation: `COMPOSE_FILES="${COMPOSE_FILES:--f docker-compose.yml}"` and use `"${DOCKER[@]}" compose $COMPOSE_FILES ...` for `config`, `up --build -d --wait`, and the `cleanup` trap. Keep `COMPOSE_FILE` honoured for backward compatibility when `COMPOSE_FILES` is unset.
2. Add `EXPECT_DIALECT="${EXPECT_DIALECT:-postgres}"`.
3. After the existing `system.health` check, add the probe round-trip (D-13, ROADMAP criterion #3):

```bash
echo "==> RPC system.db_probe (expect dialect=$EXPECT_DIALECT)"
curl -fsS \
  -H 'Content-Type: application/json' \
  -H 'Oxidean-RPC-Version: 1' \
  -d '{"procedure":"system.db_probe","input":{}}' \
  "$BASE_URL/api/rpc" > /tmp/oxidean-smoke-probe.json
grep -Eq "\"dialect\"[[:space:]]*:[[:space:]]*\"$EXPECT_DIALECT\"" /tmp/oxidean-smoke-probe.json
```

   Then call it a second time and assert `probe_count` increased, so the smoke proves a real write, not a cached read: extract with `grep -o '"probe_count"[^,}]*' | grep -o '[0-9]\+'` and compare the two values with a numeric test that fails the script when not strictly greater.
4. Print only the dialect and the two counts — never `DATABASE_URL`, and do not `tee` the raw response to stdout (T-02-12).
5. Final line stays `echo "==> smoke OK ($EXPECT_DIALECT)"`.
  </action>
