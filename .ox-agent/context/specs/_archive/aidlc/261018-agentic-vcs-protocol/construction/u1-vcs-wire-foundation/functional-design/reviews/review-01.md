### Findings
- **R-01** [major] `rules.md` BR1.5 + `entities.md` `RefUpdateCasFields` pin an encoding serde cannot provide: "`Option<ChangesetId>` as a REQUIRED field (no serde default): absent → decode error (missing_field)". serde_derive treats `Option<T>` fields as implicitly optional — an absent key decodes to `None`, indistinguishable from explicit `null`, and **no** `missing_field` error is raised. Implemented literally, a `vcs.ref_update` input omitting `new` decodes identically to `"new": null` → delete — the exact silent-delete hazard the rule exists to prevent. Required-nullable needs a non-`Option` field type (a `Nullable<T>`/newtype with custom `Deserialize` accepting `null`, or `serde_json::Value` + boundary validation — note `oxidean-core` carries only serde/serde_json/schemars, and the existing `icon_name: Option<Option<String>>` at `action_types.rs:491` does not distinguish absent/null either). The developer contribution flagged this as blocker 3; the published yaml still asserts the wrong mechanism in both files. The behavioral pin is right — pin a correct mechanism.
- **R-02** [minor] `entities.md` `RepoActivityItem` widening lists `ref_name`/`before_oid`/`after_oid`/`commits_count` — but the wire DTO fields are `ref_name`, `ref_short`, `before`, `after`, `commits_count` (`crates/oxidean-core/src/repo_types.rs:521-537`; `before_oid`/`after_oid` are the DB column/façade arg names, `crates/oxidean-db/src/repo_activity.rs:14-16`, `lib.rs:4525-4534`). `ref_short` is derived from `ref_name` (`activity.rs:33-39`) — its rule when `ref_name` is null is unpinned. Pin the wire field names `before`/`after` (+`ref_short`) or codegen emits `before_oid`/`after_oid` and breaks the `repo.activity.list` wire instead of widening it.
- **R-03** [minor] Naming drift: `entities.md` summary says "Ten wire entities" (the yaml lists 12) and refers to `StatusView`/`RefView`; the actual entities are `VcsStatusResponse`/`VcsRefPublic`. The stale names propagate into `functional-spec.md`'s ER diagram (lines 41-42) and `traceability.json` (AC1.1.2 → "entities.md StatusView").
- **R-04** [minor] Traceability nominal mappings: AC8.1.3 → BR1.1 traces a route-prefix AC (`/api/vcs/*` under the `/api/` edge prefix — u7's route nest) to the RPC-envelope rule; nothing u1 owns exercises it. AC8.2.2 → BR1.8 covers only the u1 share (client regen + `versioning.toml`); the `required_procedures`/`CLI_PROCS`/`MCP_PROCS`/env-doc clauses land in u8/u9/u7. Mark these partial-share or name the owning unit so intent-level rollup doesn't overclaim.
- **R-05** [minor] `VcsRefPublic.changeset_id` is pinned `changeset_id|null`, but C1's frozen `ref_list` entry shape is `{name, changeset_id, updated_at}` — non-null (a listed ref always points at a changeset). Nullability is pinned only for `ref_update`'s output (`{ref, changeset_id: string|null}`). Either split the two uses or record the deliberate widening vs the freeze.
- **R-06** [minor] Registration sequencing unpinned: BR1.8/WF2 include "PROCEDURES entry + dispatch arm" in the five-surface check while WF2.3 notes "u7 lands the handlers". `procedures_list_matches_dispatch` (`rpc.rs:1852`) fails on any PROCEDURES entry without a dispatch arm — so if u1's bolt lands the PROCEDURES entries before u7's arms exist, the build breaks. Pin where the entries land (u1 + stub arms, or PROCEDURES+arms together in u7).
- **R-07** [minor] `functional-design-questions.md` Q5 says rpc-gen regenerates "from the Rust types"; mechanically `rpc_gen.rs` is one hand-maintained TS string literal (verified: `rpc_gen.rs:11+`, `WIRE_VERSION` literal at :13) — BR1.8's "hand-maintained rpc_gen.rs template" is the accurate framing; reconcile Q5's wording. Also BR1.8's `[[component]]` pin omits `manifest_path`/`tag_prefix`/`changelog_path`, which every crate entry requires (versioning.toml:19-27) and which `version-check` validates for workspace membership (scripts/versioning/commands/check.ts:111-119).
- **R-08** [minor] `ErrorData.forbidden.verdicts` typed `ProtectionBlockReasons` under a `verdicts` key: C1 pins `data:{verdicts:[…]}` (bracket reads array-ish), while the git-push precedent emits the bare `ProtectionBlockReasons` struct as `data` (protection/mod.rs:247-253) — no `verdicts` wrapper. Pin explicitly whether `verdicts` is the struct or a list, and soften the "same shape a git push denial does" claim (the verdict path is identical; the envelope shape adds a key).
