The core concurrency design verifies well against the shipped surfaces: the `admission_lock` choreography is genuinely airtight for the common interleaves (proc clones the entry's lock Arc before the guard wait; the task's release→recheck→claim holds it across the section; a stale commit can only land while a live drainer exists), `emit_terminal`'s CAS-inside-buffer-lock gives the BR5.4 first-wins property, the wrapper-owned release covers all exit shapes per BR5.3, the crate edges (`api-oxpilot → api-core`, never reverse) are respected, and the fd constants are reproduced correctly almost everywhere. The blocking problems are pin fidelity, not mechanism soundness: the C6 component-catalogue row misstates three contract-visible shapes (ToolSpec fields, the `ToolOutput` return type, the slot field's name+optionality), one terminal code contradicts two upstream pins, and the tool-result content cap contradicts the entities pin — four places where a developer gets two irreconcilable answers from approved artifacts.

### Summary

The mechanism design is sound — the admission-lock seam, first-wins terminal CAS, and wrapper-owned release all check out against the shipped `ActiveTurns`/`spawn_turn_task` code and the fd's airtight-seam pins. It is blocked on pin fidelity, not architecture: the C6 catalogue row publishes a `ToolSpec`/`invoke` shape and a slot field that contradict both the contract and this unit's own entities/functional-spec, plus two wrong bound/code values (`no_provider`, `≤2KiB` tool content) that disagree with reviewed pins — all localized fixes, but four Majors exceed the READY bar.
