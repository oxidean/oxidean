## Findings

- `make test` = `cargo nextest run --workspace` (Makefile:239) — default features only. CI: `cargo build --workspace --bins` (ci.yml:205), `cargo nextest archive --workspace` (ci.yml:207), `cargo clippy --workspace --all-targets` (ci.yml:332, Makefile:405). `.config/nextest.toml` has no `features` stanza. Grep for `all-features`/`cargo-hack` across workflows: zero hits.
- With `default = ["client"]` and `server = ["dep:oxidean-db", …]`, `ObjectStore` plus every `#[cfg(test)]` test under it compiles to **zero test binaries**. A green `make test` proves nothing about the unit. Clippy/rustfmt/`cargo doc` gates likewise skip the module (`--all-targets` ≠ `--all-features`).
- Zero crates depend on `oxidean-vcs` today (only `Cargo.toml:10` member entry + its own manifest), so feature unification won't enable `server` incidentally. TD3.7's "matching U2's 15-test pattern" fails to transfer: U2's tests run because `oxidean-db` has no feature gate. BR3.1 pins `--all-features` in prose but TD3.7 never pins it in an invocation, and no artifact claims the Makefile/CI delta.
- Fix: TD3.7 must name the command (`cargo nextest run -p oxidean-vcs --features server` or workspace `--all-features`, same for clippy/doc) and put the edit in the unit's source manifest. Also replace BR3.1's `cargo check` enforcement with `cargo tree -p oxidean-vcs` (default features) asserting zero `oxidean-db` — `cargo check` cannot prove non-linkage.

**2. MAJOR — env-var range/zero semantics unpinned; parseable values break safety invariants**
entities.md:64/BR3.7 promise "numeric ranges" but pin none. Concrete deploy-time landmines:
- `OXIDEAN_VCS_GC_GRACE_SECS=0` parses fine → cutoff = now → every unlinked object is immediately reclaimable (destroys the PUT→commit window that BR3.5/AC3.5.x rests on → `vcs.not_found:object` churn on in-flight commits) **and** every lockfile is instantly stale → SR3.3's "two gc_once invocations can never interleave" is falsified.
- Huge u64 (`18446744073709551615`): `chrono::Duration::from_std` fails and `Utc::now() - d` overflows — if code-gen clones the `lfs_gc.rs:55-57` `unwrap_or(Duration::days(7))` idiom this becomes a silent default, directly violating BR3.7's "never a silent default"; if it propagates, it's a panic path. Either way "numeric ranges" must bound grace/interval to a representable window.
- `max_object_bytes`/`repo_quota_bytes` > `i64::MAX` parse OK but fail at the `i64` bind in `vcs_insert_object_if_absent` (vcs.rs:504-530) or at the SR3.2 checked-cast site — a runtime Db error on first PUT, not the promised config error.
- `gc_interval_secs=0`: house convention is "0 disables" (`schedule.rs:18-23` + `> 0` spawn guards at 63/103/130/165); the frozen contract table (contract-summary.md:228) doesn't carry it. `repo_quota_bytes=0` = deny-all-new-links — plausible but unpinned.
- `objects_dir` naming an existing regular file → `create_dir_all` io error → host-internal, not a config error (SR3.6's promise is only about *malformed* values).

**3. MAJOR — repo-quota denial leaves the bytes on disk; physical disk is unbounded by the logical quota**
WF1.3 (functional-spec.md:26) commits file + global row *before* the repo-quota check; on `QuotaExceeded{Repo}` "file stays, globally valid content." A denied-PUT object has zero links → orphan-eligible only after `gc_grace_secs` (24h). A client can stream N×256 MiB of fresh objects, have every link denied, and still grow disk unboundedly — the repo quota never bounds physical bytes. SR3.2 pins typed denials but is silent on the residual footprint. Cheap fix already in the sanctioned delta: on `QuotaExceeded{Repo}` where this PUT's `vcs_insert_object_if_absent` returned Stored, call `vcs_delete_object_if_unlinked` + unlink the file (the conditional delete handles a raced-in link).

**4. MAJOR — the row-less sweep has no sanctioned "has row" probe; the pinned delta forces an N+1**
Pass 2 needs per-file "does a `vcs_objects` row exist," but BR3.11/TD3.4 sanction *exactly two* facade additions (`vcs_get_object_link`, `vcs_delete_object_if_unlinked`). The only existing existence probe is per-file `vcs_get_object` (vcs.rs:2287) → O(blobs) indexed queries *per pass*; `vcs_live_object_hashes` is repo-scoped (vcs.rs:698-722, 2320), and no global hash listing exists. Implementers must either accept the unbounded query chatter or break the sanction with a third method — neither is written down. Pin one: per-file probe + documented O(files) cost, or sanction a paged `vcs_list_object_hashes()` / `vcs_objects_exist(&[hash])`. (Related: `list_orphaned_objects_before` itself is an unbounded `Vec` — no LIMIT — a first pass on a large backlog is a memory + lock-duration spike.)

**5. MAJOR — lock lifecycle still underpinned; SR3.3's "never interleave" is falsifiable**
FD review F-03 remains unresolved and the NFR artifacts didn't absorb it: neither WF4 nor SR3.3/BR3.6/TD3.6 pins "remove lockfile on pass completion" (the LFS precedent does release — lfs_gc.rs:79-80). Literal implementation → every later pass skips until the file ages past `gc_grace_secs` → effective cadence silently becomes `max(interval, grace)` (24h default). Conversely a single pass longer than grace goes stale mid-run → a second `gc_once` re-acquires → two passes interleave, violating SR3.3 outright — realistic once per-pass work is O(objects) (Finding 4). Suggest: release-at-end pin + mtime heartbeat during long passes, or a separate `lock_stale_secs` bound decoupled from grace.

**6. MAJOR — no permission/umask pin on blob, tmp, or shard paths**
SR3.5 covers log contents but nothing governs the files themselves. `File::create` inherits the process umask; under a permissive deploy umask (022) private-repo blobs — and in-flight `tmp/` uploads — land world-readable. The LFS precedent shares the hole, but "no auth inside the unit" (SR3.8) makes fs perms the last line of defense on shared hosts. Add an SR pinning modes (blobs 0600, shard/tmp dirs 0700) or an explicit "requires umask ≤027" deploy note.

**7. MAJOR — shared-directory hazard is a doc note, not a guard; the sweep eats foreign shard-shaped files**
The pass-2 predicate deletes any `{2hex}/{2hex}/{64hex}` file with no vcs row. LFS objects have the identical shape (store.rs:24-27, 64-hex oids). `OXIDEAN_VCS_OBJECTS_DIR` misconfigured to the LFS/packages dir → `gc_once` silently deletes live foreign blobs. The only mitigation is prose ("never shares a dir" — contract-summary.md:227). Pin a marker claim: `ObjectStore::new` writes `.oxidean-vcs-objects`, and `gc_once`/sweep refuses (config error) when the dir is non-empty but lacks the marker — or validate against sibling `OXIDEAN_*_DIR` values in `from_env`.

**8. MINOR — TOCTOU residuals acknowledged in FD but not carried into SR3.2/traceability**
- Concurrent-PUT quota overshoot: documented in BR3.4 ("single-node limitation"), absent from security-requirements.md and traceability.json — the NFR stage should own the residual-risk record.
- Probe→count double-charge: a racing `create_tx` link landing between `vcs_get_object_link` and `vcs_repo_object_counts` makes `storage_bytes` already include `size`; `+ size` then double-counts → wrongly denies a now-existing re-reference. Rare, self-heals on retry; worth one line.
- Row-less sweep check-vs-unlink TOCTOU: a row-less file >grace that gets re-PUT (row inserted) between the sweep's no-row check and `remove_file` produces live-row-over-missing-bytes → 404 window until re-upload. Re-verify absence immediately before unlink shrinks but can't close it — record as residual.

**9. MINOR — dep-set details are wrong or underpinned**
- `bytes` is **not** house-declared anywhere — api consumes `axum::body::Bytes` (store.rs:5); Cargo.lock:785 resolves bytes 1.12.1 transitively only. TD3.2's "all house-established" is false for it, and no version is pinned — it must be `bytes = "1"` to be the same type as axum 0.8's body chunks, or the U7 stream seam stops compiling.
- `sha2` is already dual-versioned in the lockfile (0.10.9 transitive + 0.11.0 at Cargo.lock:5431/5442); pin `"0.11"` matching api Cargo.toml:51 or a third copy lands.
- `workspace = true` is only legal for `serde`/`serde_json`/`schemars`/`tokio` — root Cargo.toml:24-38 has no `sha2`/`chrono`/`futures-util`/`tracing`/`tempfile`/`bytes` entries. TD3.2 should say per-crate pins matching api's versions (chrono 0.4.45, futures-util 0.3, tracing 0.1, tempfile "3"); "tempfile … workspace-established" misdescribes a per-crate pin (api:78/96, db:23).
- `cargo machete` runs in lint (Makefile:404); feature-gated deps risk false-positive "unused" — the `[package.metadata.cargo-machete] ignored` escape hatch exists (api Cargo.toml:106-107). Preempt with a note.

**10. MINOR — FD-internal contradictions that will reach code-gen through this stage**
- WF1.4 says `put` returns `{hash: "sha256:"+digest, …}` (functional-spec.md:27) vs the bare-hash pin (entities.md:72, BR3.8) → double-`sha256:` bug at the U7 seam if implemented literally.
- TD3.3 pins `verify(hash) -> Result<bool>` while WF2.3 says "mismatch ⇒ internal error" — `Ok(false)` semantics undefined (is corruption `Ok(false)` or `Err`?).
- Stream chunk errors (`E: Display`, store.rs:43 precedent) have no pinned `ObjectStoreError` variant — a client mid-body abort currently maps to host-internal 500 instead of a client-fault surface.

**11. MINOR — ops/scale notes missing for deploy realism**
- No fsync/dir-fsync pin: crash-after-ack can strand a row over lost bytes (LFS has the same hole — decide deliberately, don't inherit silently).
- `tmp/` must share a filesystem with shard dirs for rename atomicity — true by construction (subdir) but breaks if an operator bind-mounts `tmp/`; pin the assumption. NFS/overlayfs degrades `create_new` lock + rename semantics — pin "local POSIX fs" in the U7 deploy docs.
- Default `./var/vcs-objects` is process-CWD-relative (house precedent: compose api CWD=`/`, .env.example:20-31) — note for multi-binary deployments.
- `#[cfg(all(test, feature = "server"))]` on the test module (or `tests/` + `required-features`) must be pinned, or default-feature `cargo test` silently runs zero U3 tests even *with* the Finding-1 fix.
- Empty shard dirs accumulate post-GC (bounded at 65536 — note only); `.gc-lock` name diverges from LFS's `.gc.lock` (cosmetic).

**12. MINOR — tmp-beside-shard trap in the cited precedent**
TD3.2/WF1 pin `tmp/{pid}-{counter}-{nanos}.tmp` under `tmp/` — correct — but the precedent `put_stream` writes tmp *inside the shard dir* (`final_path.with_extension("tmp")`, store.rs:53). An implementer cloning it literally produces shard-dir `*.tmp` files that WF4.3's `tmp/`-only sweep never collects **and** reintroduces the shared-tmp race Q2 claims to fix (two concurrent same-hash PUTs share one tmp path). Pin "tmp lives only under `tmp/`, never beside the shard" and extend the sweep to stray `*.tmp` under shard dirs, or accept the leak.
