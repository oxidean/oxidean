# Infrastructure Design — Questions (u4-vcs-changeset-core)

Library unit — no deployment surface of its own; runtime resources are the host's (DB via the facade, object bytes via U3's `ObjectStore`). The produce set is cicd-pipeline.md + traceability.json. U3 already landed the `vcs-server` leg, the `--features server` archive flag, and the Makefile arms — U4's test suite rides all of them unchanged. The one genuinely new CI question is `dialect_vcs.rs`, because U4 is the first unit whose correctness is **dialect-divergent** (MySQL 0054 collation/width migration; CAS `actual`-read semantics differ across all three engines).

**Q1 — Does `dialect_vcs.rs` execute in CI, or stay local/Docker-only?**

[Answer]: It executes — widening the existing `db-dialects` leg costs one filter expression and zero new jobs, services, or artifacts. The leg (ci.yml:763-816) already boots postgres:16-alpine + mysql:8.4 services and runs `cargo nextest run --archive-file … -E 'binary_id(oxidean-db::dialect_probe)'` per dialect. Change the filter to `-E 'binary_id(oxidean-db::dialect_probe) or binary_id(oxidean-db::dialect_vcs)'`: both test binaries share the same `db.migrate()`-then-exercise shape, the same `DATABASE_URL` gate, and the same `SERIAL` mutex convention (the sqlite leg already passes `--test-threads=1`, serializing both binaries' tests). Considered and rejected: (a) keep `dialect_vcs` local/Docker-only — leaves the MySQL 0054 collation migration and the MySQL-vs-pg/sqlite CAS `actual`-read divergence with zero CI execution; those are precisely the behaviors that break per-dialect and nowhere else; (b) a second dedicated leg — a whole runner boot for a 2-binary filter delta on a job that already pays for the services. Residual: the widened leg now runs ~2× the per-dialect tests; wall time stays trivial (probes are sub-second; the vcs suite adds small create/CAS round-trips).

**Q2 — What does `dialect_vcs.rs` need from the environment beyond `DATABASE_URL`?**

[Answer]: Nothing new. `db.migrate()` inside the test applies the migration chain including 0054 (`0054_vcs_key_collation.sql`) — MySQL gets the real `MODIFY COLUMN` statements (four ALTERs: `index_key` width+collation, `refs.name`, `file_changes.path`, **and `file_changes.old_path`** — the fourth keeps the rename path-pair symmetric; leaving it case-insensitive risks ERROR 1267 on any future predicate mixing the pair), postgres/sqlite get the comment-only parity files (filename-parity contract from `migration_parity`, which rides the default archive in api-rust shards as a normal unit test). The test then exercises the facade across dialects: `vcs_create_changeset_tx` multi-row transaction, `vcs_cas_ref_update` arm coverage (applied, absent-row conflict, `actual`-value conflicts on both observe paths), sentinel error text (`vcs.not_found:parent` etc. whole-string matching), case-variant ref/path/old_path round-trips under the 0054 binary collation (MySQL) — and skips gracefully with `eprintln!("skipping: DATABASE_URL unset")` locally, matching `dialect_probe`'s contract.

**Q3 — Any infra/resource provisioning to design?**

[Answer]: None. U4 adds no runtime config beyond what U3 established (`OXIDEAN_VCS_OBJECTS_DIR`); read-side object reads consume U3's store. No new services (db-dialects' postgres/mysql are already booted), no new artifacts (the vcs test binary ships inside the existing `nextest-archive` — oxidean-db tests are default-feature, so `dialect_vcs` compiles into the archive under the unchanged `cargo nextest archive --workspace --features server`), no Makefile changes (the `-p oxidean-vcs --features server` arms cover the crate suite; `dialect_vcs` is an oxidean-db test reached only through DATABASE_URL invocation — a `make test-db-dialects` helper stays out of scope; local repro is the plain `DATABASE_URL=… cargo test -p oxidean-db --test dialect_vcs` invocation — `db-matrix` extension is deferred to build-and-test (Makefile is fingerprint-bound to u3's source manifest; see cicd-pipeline.md's deferral section)).
