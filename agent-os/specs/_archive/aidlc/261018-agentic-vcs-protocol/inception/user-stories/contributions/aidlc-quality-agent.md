## Contribution

Testability review of `stories.md` against the repo's idiom (nextest + real SQLite, Vitest, Compose smokes, fail-closed registry coverage). Findings ordered roughly by severity.

1. **(blocking — global; AC1.2.1, AC3.1.3, AC3.2.2, AC3.5.2, AC4.2.2, AC5.1.1, AC8.3.2)** No error-shape AC exists. Nine ACs say "a typed error" without naming the code or payload fields, so a pass/fail is interpretive (`vcs.conflict` vs `vcs.unknown_ref` vs `vcs.not_found`?). AC1.2.2 is the model — it names `db.not_configured`. Either name the code per AC or add one AC pinning the error envelope + a code manifest; P4's deterministic-error-code ask (personas.md L44, NFR5/NFR8) depends on it.
2. **(blocking — US5.1)** The failure mode CAS exists to kill has no AC: two *concurrent* `ref_update` calls with the same `expected_old` must yield exactly one winner, loser gets the conflict error, ref equals winner's target. AC5.1.1's sequential stale-check passes even a non-atomic check-then-set. Add the two-call race AC (G2's intro already blesses "two simultaneous calls" as the test shape).
3. **(blocking — AC1.2.1, US8.5/US8.6)** Object routes have no authz/disable negative ACs. AC1.2.1 names failing writes (`changeset_create`/`ref_update`) and surviving reads (incl. object GET) but never says whether object PUT fails with the flag off — FR1.4 "stops new writes" implies yes; a test writer can't tell. And no AC asserts `/api/vcs/{owner}/{repo}/…` enforces repo read/write ACL — a valid PAT without repo access must be denied (FR14.3); only the cookie-never negative (AC8.5.1) exists.
4. **(blocking — G4, US2.4/2.5, changeset_get)** Systematic missing negative path: unknown/malformed identifier handling. `log`, `diff`, `tree`, `file_get`, `blame`, `path_history`, `merge_base`, `merge`, `rebase` on nonexistent changesets/paths — typed not-found vs empty result is unspecified. Only AC3.2.2 pins unknown-hash → not-found (objects). Add a per-story AC or one blanket "unknown id → typed error" AC.
5. **(suggestion — US2.2/AC2.2.1)** Covers sequential resubmit only; the racing case is untested — two simultaneous identical `changeset_create` calls must both return the same id with exactly one row (unique-key race), distinct from AC2.3.1 (same parent, different content).
6. **(suggestion — AC7.3.1)** "Behave byte-for-byte as before" has no defined baseline — the only AC on a Must-Have story isn't pass/fail. Replace with an enumerated checklist: `git push`/`fetch`/`clone` succeed, PR merge + release succeed, web pages return unchanged responses on a VCS-enabled repo.
7. **(suggestion — AC2.3.2)** Atomic boundary is ambiguous: "objects + row + derived rows commit together" conflicts with AC3.1/AC2.1.1 where objects arrive via earlier independent PUTs (those can't be un-committed on failure; they're refcounted orphans per FR3.3). Specify the atomic unit = changeset row + derived rows + inline-content objects only, or the fault-injection test can't be written.
8. **(suggestion — AC2.1.3)** "Serialize nothing and never contend on a global lock" is an unobservable internal negative — violates Q5's wire-level AC rule and duplicates AC2.3.1 + NFR2. Drop or rewrite as the observable N-concurrent-creates-succeed claim.
9. **(suggestion — US2.4/2.5)** Missing merge/rebase edge ACs: merge of changesets with no common ancestor (AC4.2.2 defines typed no-ancestor only for `merge_base`), merge of identical/already-ancestor changesets (fast-path or no-op result unspecified), rebase conflicts covered but cycle/descendant targets not.
10. **(suggestion — US3.5)** GC-vs-reference race untested: an object referenced by a changeset created concurrently with a GC tick must never be reclaimed (check-then-delete race on refcount). Also AC3.5.2 "enforced at write time" doesn't say which typed error distinguishes repo-quota-exceeded from object-size-exceeded.
11. **(suggestion — AC4.1.2)** Prescriptive mechanism claim ("computed via the derived-data mechanism … not a brute-force scan") is unverifiable at the wire and redundant — NFR1 already carries the real pass/fail (bounded visit-count nextest). Defer to NFR1 or cut.
12. **(suggestion — AC4.1.1)** "Per-entry metadata" doesn't name fields, and no AC bounds `vcs.log` output — pagination/limit semantics on deep history are unspecified, so the expected response size is interpretation. Name the fields or defer explicitly to contract-design.
13. **(suggestion — AC5.2.1)** Empty-repo ref state unspecified: on a fresh repo with zero changesets (AC1.1.2), does `ref_list` return `main` pointing at nothing? Also whether non-fast-forward CAS moves (given correct `expected_old`) are permitted — "diverged heads reconcile only via merge" hints no, but the permission/denial path is unstated.
14. **(suggestion — AC8.6.1 vs AC1.1.1)** Mapping gap: AC1.1.1 requires admin/owner for `repo_enable`, but AC8.6.1 describes only a read/write split "mirroring repo permissions." The proc→class table needs a third tier stated (or repo_enable named admin-class), else the coverage test can't be authored.
15. **(suggestion — G6)** Missing working-copy failure ACs: checkout interrupted mid-write leaves what on disk (AC3.3.3 covers cache corruption, not the target tree — AC6.1.1); checkout into a non-empty/conflicting target dir; a corrupted-on-disk cache entry must be detected by hash-verify on read (AC6.2.1 only proves hit-avoidance).
16. **(suggestion — AC7.2.2)** Export onto an existing, diverged Git branch: fast-forward-only or force? The protection-verdict parity AC is good but the ref-move precondition is unstated.
17. **(nit — AC3.2.1)** "Long-lived cache semantics" unquantified — assert the concrete header (e.g. `Cache-Control: immutable, max-age=…`) or the pass threshold is reviewer taste.
18. **(nit — AC1.3.3)** "Per the repo record's archival semantics" delegates the expected result to an undefined referent; state the observable (reads succeed, writes denied — or whichever archival means).
19. **(nit — AC6.3.1)** "Supported platforms" undefined — symlink/exec-bit assertions differ on Windows; name the platform set the test must pass on.
20. **(nit — AC3.1.1, AC3.3.3, AC8.3.3, AC8.4.2)** Implementation-prescriptive ACs contradicting Q5's own answer: on-disk shard path, "(temp-write-then-rename or hash verify)", crate-placement claims. Same for AC8.5.2 "reuses the sha256 path" and AC1.1.3's modal "may serve."

## Positions

Endorse — these must survive integration:

- **Wire-level AC style + FR tagging (Q5/Q6 answers).** The "observable request/response or state transition" contract is right; the fixes above are conformance to it, not a style change.
- **AC1.2.2** — the only AC that names its error code (`db.not_configured`); use it as the template for finding #1.
