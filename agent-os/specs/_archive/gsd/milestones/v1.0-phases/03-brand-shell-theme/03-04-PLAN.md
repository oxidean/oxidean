<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API `system.health` response → status DOM | Server-controlled `version` / `database` strings rendered to every visitor of a public page |
| Network failure / rejected fetch → error UI | Exception detail could leak infrastructure information into the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-12 | Injection (XSS) | rendering `version` / `database` | mitigate | Both values are interpolated as JSX text children only (`version {phase.version} · database {phase.database}`) — React escapes them; no `dangerouslySetInnerHTML`, no `href`/`src`/`style` value derived from the response |
| T-03-13 | Information disclosure | unreachable-state copy | mitigate | The catch branch renders the fixed UI-SPEC string and never the caught error: no `String(e)`, `e.message`, or `e.stack` reaches the DOM or `console` |
| T-03-14 | Denial of service | health polling | mitigate | Exactly one health request per mount, guarded by the existing `cancelled` flag; no `setInterval`, no retry loop, no automatic refetch (also keeps D-26 "live health only") |
| T-03-15 | Information disclosure | public unauthenticated status page | accept | `/status` is public by prior decision (Phase 1 D-25) and exposes only version and dialect name, which Phase 2 already surfaces through `system.health` |
</threat_model>
